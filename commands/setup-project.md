Set up a Python project for the Claude command system: `.claude/checks.sh` + `.claude/project-params.md`. $ARGUMENTS

Run this once per project, before the first /dev run:

- **`.claude/checks.sh`** — the toolchain contract (`test | lint | security | all`) that /dev,
  /work, /dev-finish and /pr invoke.
- **`.claude/project-params.md`** — a discovery cache that /review and /ui-test read as a
  shortcut instead of searching the repo from scratch.
- **`.gitignore`** — appended, never rewritten, for the run artifacts /work and /dev leave
  behind (Step 4a).
- **`.gitattributes`** — appended, so a committed `.sh` survives `core.autocrlf` (Step 4b).
- **`.githooks/pre-push`** — refuses pushes straight to the trunk (Step 4c).

The first two are generated data, overwritten freely. The last two are git-level and
user-owned: append-only, and never silently replaced.

Both are data, not code: the command files themselves stay global in `~/.claude/commands/` and
are never copied into the project, so updating a master command applies everywhere at once.

## Step 1: Discovery

**Python toolchain (for `checks.sh`):**

- Confirm this is a Python project (`pyproject.toml`, `setup.py`/`setup.cfg`, or
  `requirements*.txt`). If not → STOP and report; this command is Python-only by design.
- Detect the source layout: `src/<pkg>/`, a top-level package dir, or flat. Detect the test
  dir (`tests/`, `test/`).
- Detect available tools with `python -m <tool> --version` (and `command -v lint-imports`):
  `ruff`, `bandit`, `pip_audit`, `mypy`, `import-linter`. Note what's missing — the script
  SKIPs missing optional tools at runtime, so this is for the report, not a blocker. Only
  `ruff` and `pytest` are load-bearing.

**Project shape (for `project-params.md`)** — detect automatically, no discovery questions:

- **Trunk branch** — `git symbolic-ref --short refs/remotes/origin/HEAD` (strip `origin/`); if
  unset, local `main`, then local `master`, first existing wins. If none exists, use the
  current branch and note that in the report.
- **Guideline docs** — `CLAUDE.md`, `CONTRIBUTING.md`, `.editorconfig`, linter configs.
- **Architecture docs** — `ARCHITECTURE.md`, `docs/architecture*`, `docs/design*`.
- **Review template** — `docs/code-review-template.md` or similar.
- **Tests** — framework (pytest/etc.), test dir, file-naming pattern.
- **Framework** — read imports and manifests: PySide6/PyQt/tkinter, Django, FastAPI, or a JS
  framework in a `package.json`. Note the UI layer specifically (UI file locations, style
  definition files, UI test dir + the exact runner command), or "none" if there is no UI.

For **fullstack/monorepo** projects, identify each part separately (e.g. "React frontend in
`client/`, FastAPI backend in `server/`").

## Step 2: Generate `.claude/checks.sh`

If the file already exists: show its content and ask whether to overwrite (the only permitted
prompt). If it carries the generated-by stamp and is identical to what would be generated,
report "up to date" and skip.

Write the template below, substituting ONLY the `SRC=` and `TESTS=` lines with the ACTUAL
detected paths. Do not otherwise edit it — it is mirrored in this repo at
`templates/checks.sh`, and the two must stay byte-identical apart from those two lines.

```bash
#!/usr/bin/env bash
# generated by /setup-project — toolchain contract for the Claude command system
# subcommands: test | lint | format | arch | types | sec | security | all   (exit 0 = green)
#
# Mirrors CI, so "green here" means "green in CI". Checks whose tool isn't
# installed are SKIPPED with a warning, so this stays usable on projects that
# haven't wired every tool yet. `all` runs EVERY check and reports ALL failures
# rather than stopping at the first — /dev and /work report which stage failed.
set -u

SRC="<SRC>"
TESTS="<TESTS>"

# True if a tool is runnable via `python -m <name>`.
have() { python -m "$1" --version >/dev/null 2>&1; }

run_lint()   { python -m ruff check "$SRC" "$TESTS"; }
run_format() { python -m ruff format --check "$SRC" "$TESTS"; }
# import-linter uses the `lint-imports` console script, not `python -m`.
run_arch()   { if command -v lint-imports >/dev/null 2>&1; then lint-imports; else echo "SKIP: import-linter not installed"; fi; }
run_types()  { if have mypy; then python -m mypy "$SRC"; else echo "SKIP: mypy not installed"; fi; }
# QT_QPA_PLATFORM is harmless on non-GUI projects and required for headless Qt.
# Extra args narrow the run to specific paths (`checks.sh test tests/test_foo.py`),
# so callers never need to bypass this wrapper and lose the env var.
run_test()   { QT_QPA_PLATFORM=offscreen python -m pytest "$@"; }

run_sec() {
  local rc=0
  if have bandit;    then python -m bandit -q -r "$SRC" || rc=1; else echo "SKIP: bandit not installed";    fi
  if have pip_audit; then python -m pip_audit           || rc=1; else echo "SKIP: pip-audit not installed"; fi
  return $rc
}

run_all() {
  local rc=0
  run_lint   || rc=1
  run_format || rc=1
  run_arch   || rc=1
  run_types  || rc=1
  run_sec    || rc=1
  run_test   || rc=1
  return $rc
}

case "${1:-all}" in
  test)   shift; run_test "$@" ;;
  lint)   run_lint ;;
  format) run_format ;;
  arch)   run_arch ;;
  types)  run_types ;;
  sec|security) run_sec ;;
  all)    run_all ;;
  *) echo "usage: checks.sh {test|lint|format|arch|types|sec|all}" >&2; exit 2 ;;
esac
```

Create the `.claude/` directory if missing. If `ruff` is not installed, still generate the
script but WARN prominently in the report — `lint` and `format` will fail until it's installed.

Note for existing projects: this template's `all` is STRICTER than the pre-2026-07-31 one —
it adds `ruff format --check`, and it no longer stops at the first failure. A project that was
green before can legitimately go red on formatting the first time. Report that as the
project's state; do not fix it here (Step 5 rules apply).

## Step 4: Git hygiene

Two guards written once per project. Both are structural — they hold whether or not an agent
remembers a rule.

### 4a — Ignore run artifacts

`/work` and `/dev` leave scratch files in the project root. Nothing ignores them by default,
so a `git add -A` sweeps them into a commit — `work.md` carries a standing rule telling the
agent to avoid exactly that, which is a behavioural guard where a structural one belongs.
It mattered little while everything stayed local; `/pr` pushes what is tracked.

**`.gitignore` is user-owned and not regenerable** — unlike the two files above. So:
append only, never rewrite or reorder existing lines, and skip any pattern already present
(by exact match anywhere in the file). Re-running this command must add nothing the second
time. Create the file if it is absent.

```gitignore
# Claude command-system run artifacts (added by /setup-project)
.dev-state.md
.dev-log.md
.dev-plan.md
.dev-plan.*.done.md
.dev-archive/
.work-context.md
.claude/settings.local.json
```

If every pattern is already present, report "up to date" and write nothing. Report which
lines were added. `.dev-plan.md` is the one debatable entry — it is user-authored input
rather than generated state, so say so in the report and let the user drop it if they want
plans versioned.

### 4b — Keep shell scripts LF

`core.autocrlf=true` is Git for Windows' default (system-level on this machine). A `.sh` file
committed without a `.gitattributes` rule is checked out as CRLF, and bash then dies on
`$'\r'` — or worse, `SRC="src"` becomes `src\r` and the failure reads as a broken repo layout
rather than a line-ending problem.

The locally generated `checks.sh` is unaffected, since it never round-trips through a
checkout. This only bites once a project commits it — and then it bites every fresh clone,
breaking `/work`, `/dev`, `/dev-finish` and `/pr` at once. Two lines prevent it, so append
them (same append-only rules as 4a):

```gitattributes
# Shell scripts must stay LF or bash dies on \r (added by /setup-project)
*.sh text eol=lf
```

Skip if an equivalent rule is already present. Create `.gitattributes` if absent.

### 4c — Trunk push guard

`/pr` refuses to run on the trunk, but that only guards the `/pr` path — a plain `git push`
walks around it. This hook covers every push from this clone, which matters most on projects
whose trunk has no server-side protection (private repos on GitHub's free plan cannot enable
branch protection at all).

The guard must not block the maintainer, who legitimately pushes the trunk after merging
locally. So the hook is **versioned once and opted out of per machine** — same file for
everyone, different behaviour depending on a local git config flag.

Write `.githooks/pre-push`:

```bash
#!/usr/bin/env bash
# installed by /setup-project — refuses pushes to the trunk unless this clone opts in.
# Maintainers who merge locally and push the trunk: git config claude.allowTrunkPush true
if [ "$(git config --bool claude.allowTrunkPush 2>/dev/null || echo false)" = "true" ]; then
  exit 0
fi
while read -r _local_ref _local_sha remote_ref _remote_sha; do
  case "${remote_ref#refs/heads/}" in
    main|master|trunk)
      echo "pre-push: refusing to push directly to ${remote_ref#refs/heads/}." >&2
      echo "  Open a pull request instead (/pr)." >&2
      echo "  Maintainer? git config claude.allowTrunkPush true" >&2
      exit 1
      ;;
  esac
done
exit 0
```

Then, in this clone: `git config core.hooksPath .githooks`, and mark the file executable so
Git for Windows will run it: `git update-index --add --chmod=+x .githooks/pre-push`.

**`core.hooksPath` is per-clone config and is NOT committed.** Only the hook *file* is
versioned, so a fresh clone gets a dormant file and no guard — which is the one developer the
guard exists for. Committing the hook is therefore not enough on its own. Report this
explicitly, with the line every other clone must run once:

```
git config core.hooksPath .githooks
```

If the project has a CLAUDE.md, say in the report that this line belongs in its setup
instructions. Do not edit CLAUDE.md here (Step 6 owns that boundary).

Rules for this step:
- If `.githooks/pre-push` already exists → show it and ask before overwriting. Never
  overwrite a hook silently; it may be the user's own.
- If `core.hooksPath` is already set to something other than `.githooks` → **do not change
  it**. Report the conflict and leave the project's existing hook setup alone.
- Say plainly in the report that `git push --no-verify` bypasses this. It stops accidents,
  not determined pushes — that is the whole of what a client-side hook can do.

## Rules

- Do NOT modify any files besides `.claude/checks.sh`, `.claude/project-params.md`,
  `.gitignore`, `.gitattributes`, and `.githooks/pre-push`. `.gitignore` and `.gitattributes`
  are append-only — never rewrite, reorder, or remove a line that was already there. An
  existing `pre-push` hook, or a `core.hooksPath` already pointing elsewhere, is left alone
  and reported.
- Do NOT fix failing tests or lint during Step 5 — report only.
- No discovery questions — auto-detect everything. Exactly two prompts are permitted: the
  `checks.sh` overwrite confirmation in Step 2 and the `pre-push` overwrite confirmation in
  Step 4c. Everything else is detected or reported, never asked.
